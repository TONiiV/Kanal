# 再次录制续写同一场会议：一条记录，多段录制

状态：accepted，2026-09-23。

推翻 [ADR 0054](0054-meeting-record-lifecycle-and-storage.md) 的决定 1、决定 3，以及「明确排除」
里的「一条记录装多次会话」。0054 的其余决定不变。

## 背景

操作员反馈：会中停下录制（茶歇、换议题），再按录制，得到的是一条新记录。一场会议于是散成几条，
每条只有一段转写和一段录音，标题各自生成，Markdown 导出和迁移包也只各带一段。操作员要的是：
同一场会议里停了再录，**接着写进同一条记录**。

0054 当初排除这件事的理由是真实的：每次 Start 必换 `RoomId`，ASR 的 utterance id 归零，把两次
会话写进同一个 `transcript.jsonl` 会按 id 互相覆盖。本文保留这个前提，只换解法——不共用文件。

## 决定

1. **段（run）。** 一条记录由若干段组成，一段 = 一次 Start…Stop。第 1 段写 `transcript.jsonl`
   与 `audio.wav`；第 n 段（n ≥ 2）写 `transcript-{n}.jsonl` 与 `audio-{n}.wav`。每个转写文件保持
   自己的 id 空间，文件里的 id 不改写；读取整条记录时按段序拼接，id 在内存里加段号前缀
   （`2/u1`），不会撞。
2. **`meeting.json` 是段的清单。** 新增有序的 `segments`：`{ transcript, audio, startedAt,
   endedAt }`，`audio` 在未录音时为 null。记录的 `StartedAt` = 第一段开始，`EndedAt` = 最后一段
   结束。`meeting.json` 与迁移包 manifest 的 schema 升到 2；读取接受 1 与 2，写出一律 2。schema 1
   的记录按一段读（旧的 `transcriptFileName` / `audioFileName`）。工作空间与注册表文件仍是 1。
   旧版本会拒绝打开 schema 2 的记录——这是 0054「拒绝而不是读一半」的规则本身。
3. **信任边界。** `segments` 里的每个文件名都按「纯文件名」校验：拒绝 `..`、分隔符、绝对路径与
   `C:x` 这类盘符相对路径。不合格的条目让整条记录报为损坏，绝不跟随。迁移包的 manifest 同样校验，
   且只解出清单里点名的文件。
4. **绑定规则（取代 0054 决定 3）。** 选中空白记录 → 用它，作为第 1 段；选中已结束的记录 → 续写
   为下一段；什么都没选 → 新建。「新建会议」按钮仍是另起一场的方式。知情确认弹窗在续写时写明
   续的是哪一场（`consent.continue`）。取消确认：磁盘上什么都不变。启动失败：`meeting.json`
   恢复原样，不留新段，也不留 `transcript-{n}.jsonl` / `audio-{n}.wav`（文件在会话启动成功后才
   创建）。
5. **屏幕。** 续写时，先载入之前各段的句子，再接实时句子；标题保持记录上的标题，不自动重命名。
   段与段之间不加分隔线（需要给气泡加属性并改模板，本次不做）。
6. **所有读取方按段序读全部段：** 浏览、Markdown 导出、刻度尺、文件页签、迁移包导出／导入
   （全部转写；录音仅在勾选时；清单在 manifest 里）、删除（删整个文件夹，天然覆盖）。
   导入时保留每一段，即使该段的转写没有随包到达：下一段的编号取段数，缺一段就会撞上已有文件。

## 明确排除

- **手机端只收到当前段。** 中继频道仍随每次 Start 更换；迟到的参与者看不到之前各段。
- **发言人标签按段重新开始。** 第 2 段的 S1 与第 1 段的 S1 不保证是同一人；之前各段按原始标签
  显示，改名与合并只作用于当前段。
- **Markdown 导出的知情确认只写最近一段的确认时间。**
